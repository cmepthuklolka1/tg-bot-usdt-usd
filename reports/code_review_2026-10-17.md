**Уточнения по смыслу Bybit и доступу — проверить при рефакторинге**

В [bybit_p2p.py:69](/home/cmp/projects/crypto-excurs/src/services/bybit_p2p.py:69) настройка суммы означает только `maxAmount >= X`. Если X задуман как сумма вашей сделки, нужен также `minAmount <= X` и достаточный доступный объём, иначе предложение с минимумом 200000 может попасть в таблицу для 50000. Если это именно порог максимального лимита продавца, фильтр соответствует смыслу, но подпись «сумма сделки» вводит в заблуждение. Произвольная сумма 150500 в общих меню сокращается до `150K`: [user.py:152](/home/cmp/projects/crypto-excurs/src/handlers/user.py:152).

Проверка whitelist есть на входе в меню, но отсутствует в ряде последующих FSM-обработчиков. После отзыва доступа пользователь с незавершённым состоянием может продолжить менять свои настройки. Централизованный фильтр доступа и отдельный фильтр администратора уменьшат этот риск и количество повторяющихся проверок. У административных FSM-обработчиков также стоит явно ограничить допустимый тип сообщения: сейчас фото вместо ID/имени приводит к обращению к `None.isdigit()` / `None.strip()`. Подтверждений эксплуатации нет; прямого обхода прав администратора через обычного пользователя не установлено.

**Предлагаемое поведение уведомлений**

Это целевой дизайн, а не описание уже реализованных возможностей. Пороги — начальные настройки для проверки на реальной нагрузке.

| Ситуация | Поведение бота | Что сообщать |
|---|---|---|
| Единичный таймаут | Ограниченный retry, доступный резерв; в отчёте статус источника | Не требовать входа; краткий сбой можно оставить только в журнале |
| Ошибки продолжаются, например 2–3 проверки / 2 минуты | Открыть инцидент, включить опрос восстановления раз в 60 секунд | «Сетевой сбой. Перевыпуск токена не требуется. Проверяю автоматически» |
| Свежий курс снова получен | Закрыть инцидент | Один раз «Курс снова доступен. Сбой длился …; действий не требуется» |
| Получен только резервный курс | Оставить состояние `degraded` | Указать, какой курс получен; восстановление основного отмечать отдельно |
| Access token отвергнут | Один согласованный refresh и повтор запроса | Не требовать ручного входа до результата refresh |
| Refresh недоступен по сети / HTTP 5xx | Повторить позже, использовать действующий access token, если возможно | «Не удалось связаться для обновления авторизации», без утверждения о неверном токене |
| Refresh явно отвергнут как недействительный | Открыть инцидент авторизации | Нужен повторный вход; дать точную инструкцию загрузки и подхвата токенов |
| Файл отсутствует или повреждён | Не затирать известное рабочее состояние | Сообщить именно о конфигурации, а не о сетевой ошибке |

Пример предупреждения при длительном сетевом сбое:

> ⚠️ Antarctic Wallet: временный сетевой сбой.
>
> Не удалось получить курс за 15 секунд. Перевыпуск токенов не требуется.
> Последний успешный курс: …, получен … назад.
> Следующая автоматическая проверка — через 60 секунд.

Пример восстановления:

> ✅ Antarctic Wallet: курс снова доступен.
>
> Соединение восстановлено в … МСК. Сбой длился … . Действий не требуется.

Время следующей проверки можно обещать только после реализации отдельного опроса восстановления. Уведомления должны отражать качество источника: успешный резерв не означает восстановление основного endpoint.

**Порядок рефакторинга**

1. **Отдельное исправление уведомлений:** типы ошибок, осмысленные действия, состояние инцидента, сообщение о восстановлении и самостоятельная перепроверка. Сначала закрыть сценарий из обращения.
2. **Надёжность Antarctic:** retry/fallback внутри каждого endpoint, единый бюджет времени, атомарное сохранение токенов, подхват ручной замены, объединение refresh. Отдельно обработать ошибки диска и изменения схемы ответа.
3. **Надёжность Telegram:** общий компонент обновления закрепления с типизированной обработкой ошибок, блокировка на чат, ограничение размера отчёта. Не уничтожать работающий отчёт ради временного placeholder.
4. **Разделение обязанностей:** сервисы возвращают `SourceResult` с данными, источником, статусом и временем; отдельный агрегатор собирает снимок; renderer форматирует; notifier ведёт инциденты; `user.py` оставляет только обработку интерфейса. Telegram-зависимость убрать из менеджера токенов.
5. **Эксплуатация и воспроизводимость:** обработать GitHub credential, ограничить права секретов, добавить CI и проверку версии при запуске. Улучшать deploy после появления быстрых регрессионных тестов.

Для этого размера проекта достаточно нескольких явных компонентов. Микросервисы и обязательная миграция всех JSON в БД сейчас не обоснованы. Для состояния инцидентов и последнего успешного курса подойдёт небольшой атомарный JSON или SQLite; выбор зависит от необходимости истории и конкурентной записи. В текущем storage атомарна отдельная запись, но не вся операция read–modify–write; это станет существенным при добавлении потоков/нескольких процессов. Потеря обновлений в нынешнем единственном event loop не доказана.
